# What Snapper does to your game

Snapper is an observer, and an observer can cause the bug it reports. This page lists what the host does to a page in each mode, so "was it Snapper?" can be answered from facts. It is written from the code (`packages/host`, Snapper 1.4.1) and was reviewed against it claim by claim by a second AI agent, three times. If a sentence here stops being true of the code, that is a bug.

## Play (`snapper play`, the launcher's Play)

**Where the game runs.** One Electron 44.9.0 window (Chromium 152) for the game, plus one hidden `about:blank` window the host uses to compose the `before/` contact sheet (it never loads the game). A folder target is served by a static server in the host process, bound to `127.0.0.1` on a random port; a URL target is loaded as given. The server sends `Cache-Control: no-store, no-cache, must-revalidate` on every file it serves, so assets are re-fetched each time. It is not a production server: no range requests, no compression, no ETags, a fixed MIME table (unknown extensions are `application/octet-stream`), and the game root's own `.snapper/` folder is reachable under it. The window uses a **throwaway browser profile** (`%TEMP%\snapper-host-<pid>`), deleted on a normal close (a crash or kill can leave it in `%TEMP%`): `localStorage`, IndexedDB, cookies and the HTTP cache start empty every session. The window has no menu; `contextIsolation` and `sandbox` are on and Node is off in the page; `window.open` is denied; navigation is not restricted.

**Chromium settings that differ from a stock Electron:** the switches `autoplay-policy=no-user-gesture-required`, `disable-renderer-backgrounding`, `disable-backgrounding-occluded-windows`, `disable-features=CalculateNativeWinOcclusion`, and `backgroundThrottling: false` and `autoplayPolicy: no-user-gesture-required` on the window. They exist so a game behind another window or unfocused keeps running at full rate (the intent; not separately measured). CDP focus emulation (`Emulation.setFocusEmulationEnabled`) is requested at start (a failure is ignored), so the page reports focus when it does not have it.

**Cross-origin isolation, only with `--coi`.** Every response then also carries `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Embedder-Policy: require-corp` and `Cross-Origin-Resource-Policy: same-origin`: `crossOriginIsolated` becomes true (Godot 4 web exports need it) and cross-origin assets without CORP headers are blocked. Off by default.

**What is injected into the page.**
- The SDK (`packages/sdk/snapper.js`, about 300 lines) through `Page.addScriptToEvaluateOnNewDocument`, in every frame (iframes too), before the game's first script: it defines `window.snapper`. It adds no DOM and no listeners. Its one timer, a 250 ms tape flush, starts at the game's first `tick`; `tick` itself allocates nothing, a flush with new ticks allocates two small typed arrays.
- A preload script in Electron's isolated world (the page cannot see its variables, but it runs on the page's main thread). Since 1.4 its page-side code is `packages/host/preload/page.js`, embedded verbatim (the same code attach mode injects). It exposes `window.__snapperBridge`, the SDK's channel to the host; page code can call it too (a game can raise a mark through it). It:
  - runs one `requestAnimationFrame` callback per frame that records the frame interval (for `perf.json` and the frame-pacing auto-marks) and calls `navigator.getGamepads()` (for the gamepad mark combo; pad buttons and axes are also recorded in `tape.jsonl`), every frame while the page is visible, in every mode, whether or not the game reads pads.
  - listens to `keydown`, `keyup` and `keypress` on `window` in the capture phase and records **every** key code with its time in `tape.jsonl`, including keys typed into the game's own text fields; plus `gamepadconnected`, `gamepaddisconnected` and a no-op `blur` listener; since 1.4.1, passive `pointerdown`, `pointermove` and `wheel` listeners on `window` in the capture phase that only note the time of the latest pointer event (nothing about the pointer is recorded; they exist so a mouse-only game counts as played, D-030); a 250 ms timer sends the recorded keys and pad changes to the host, and the latest pointer time when it changed.
  - owns the overlay: one `<div data-snapper-overlay>` appended to `<html>` (not `<body>`), `position: fixed`, `z-index: 2147483647`, its content in a closed shadow root, `pointer-events: none` except the note box and the F9 panel; if the page removes it, the 250 ms timer re-attaches it (in bare, the next toast or note box does). Outside bare mode a 250 ms timer redraws the chip and reports the overlay's rectangles, and the overlay is built at `DOMContentLoaded` (at once when the document has already loaded).

**What is observed.** The debugger stays attached for the whole session with the CDP domains `Page`, `Runtime` and `Log` enabled. Events used: `Runtime.consoleAPICalled`, `Runtime.exceptionThrown`, `Log.entryAdded`, `Page.screencastFrame`. With `Runtime` enabled, every `console.*` call the game makes is serialised and sent to the host, in every mode; a game that logs every frame pays that per call. Electron events used: navigation start/finish/fail, renderer crash, and `before-input-event` (hotkeys). `Runtime.evaluate` runs in the page for:
- the SDK's `ready()` (which calls the game's `stepper.seed()` when registered; `registerStepper` itself calls it once too) after the game registers, or 3 s after load if it never does, then `commandList()` when the game registered commands; on a navigation, one read of `location.href`;
- `snapper.frame()` every 500 ms for the chip, and the game's state while the F9 panel shows it (not in bare, not with the overlay hidden);
- `snapper.frame()` up to once per ring frame (never overlapping), and once at each frame-pacing drop;
- at a mark: a tape flush, then one evaluate that flushes again and reads the frame number, the game's state and its frame image;
- your actions: F6 (save state: the state), F10 and F7 (the game's `pause()`/`resume()` and `step(1)`), the F9 panel's commands, and the `exit` state when the window closes.
Page code is never rewritten (except with `--resume`, below).

**The ring buffer** (the `before/` sheet): `Page.startScreencast` (JPEG, quality 50, at most 480 px wide; each frame acknowledged with `Page.screencastFrameAck`), restarted every 3 s when the captured rate drifts outside 7.5–14 fps, aiming at about 10. The host holds the last `ringSeconds` + 1.5 s (default 5 + 1.5) in memory; a mark keeps `ringSeconds` + 0.25 s. Chromium's compositor produces and copies the frames outside the page; in the page only the `snapper.frame()` read runs.

**At a mark** (F8, the gamepad combo, `console.error`, an uncaught exception, a failed boot, a frame-pacing drop, an assert, an API mark; automatic ones have cooldowns, e.g. at most one `console.error` mark per 5 s; so a misbehaving game triggers captures by itself): the overlay is hidden, the host waits two animation frames (350 ms at most), `Page.captureScreenshot` takes `shot.png` (abandoned with a warning, and no `shot.png`, if it has not answered in 15 s), then the overlay is shown again, and the one evaluate above reads state and frame. For human marks the note box then opens and takes keyboard focus from the game. The wall time from trigger to the end of that evaluate is in `perf.json` `host.markCaptureMs`; the frames around it are measured below.

**What is never done.**
- No network interception: no CDP `Fetch` or `Network` domain; requests go straight to the server or the URL. Snapper makes no network connections of its own while you play. Two commands send something off the machine, and only when you run them: `snapper issue --github` (through your own `gh`) and `snapper issue --discord <webhook>`.
- No storage or cookie changes beyond what the game itself writes into the throwaway profile.
- No input injection while you play. A `--smoke` test script does drive the page: keys through CDP `Input.dispatchKeyEvent`, navigations through `Page.navigate`, and its `eval` steps through `Runtime.evaluate` (awaiting promises).
- Keys the game does not see: the first keydown and the keyup of a host hotkey (default F6 save, F7 step, F8 mark, F9 overlay, F10 pause, F11 fullscreen; F12 devtools, F5 and Ctrl+R reload); held auto-repeat keydowns of the configured hotkeys and Ctrl/Alt combinations of them do reach the page (their keyup does not; for Ctrl+R the R keyup does), but F5 reloads and F12 opens DevTools with any modifier (Ctrl, Alt or Shift), and Shift does not exempt a key (Shift+F8 marks). While the note box or the F9 panel's input has focus: every keydown, and every keyup except those of keys that were already held when the box opened (they pass, so nothing sticks). A keyup whose keydown it never saw. During a `--resume` restore, every keydown.
- Hotkeys act on the window and the game: F11 resizes the viewport (fullscreen), F5/Ctrl+R reload the game (a new tape segment), F12 opens detached DevTools.
- No changes to the page's DOM other than the overlay `<div>`, and none to its globals other than `window.snapper` and `window.__snapperBridge` (except with `--resume`).

**Where the files go.** `<game-root>\.snapper\sessions\<slug>\<session-id>\` (or `--out`). At the end of a session the host also writes `SESSION.html` (a derived static report, no script) next to `SESSION.md`; `summary`, `replay`, `triage`, `issue` and `import` regenerate it. Nothing leaves the machine.

## Play with `--resume`

A restore (`--resume <session> --at …`) boots the game with its pause parameter added to the URL, then for the length of the restore: mutes the window's audio, replaces `navigator.getGamepads` with one returning `[]`, blocks the player's keydowns, shows a full-screen progress overlay, and steps the game through its own stepper (`pause`, `step`, `state`). Afterwards it calls `step(0, [])` once, removes the pause parameter with `history.replaceState`, deletes the `getGamepads` override, unmutes and hands control back.

## Play with `--bare`

`snapper play --bare` (or `"bare": true` in `snapper.config.json`, or the launcher's Bare box): no continuous host-side capture.
- **Off:** the screencast ring buffer (no `Page.startScreencast`, no per-frame `snapper.frame()` read, no `before/` folder in any mark), the overlay chip, its 250 ms timer and the `DOMContentLoaded` build, the 500 ms `snapper.frame()` poll, the F9 panel (F9 shows "bare session: no overlay"), the red error flash. The overlay `<div>` is created when the first toast or note box shows (in practice at the first mark: "Mark 0001 saved") and then stays.
- **Still on:** everything else above: the SDK and its tape flush, the preload's frame-interval recorder, gamepad poll, key recorder and pointer-time listeners with its 250 ms send, the CDP domains (console calls are still sent per call), the hotkeys, the compose window (idle), and every mark file except `before/`: `shot.png` (the screenshot still runs), `frame.png`, `state.json`, `inputs.json`, `log.json`, `perf.json`, the note, checkpoints and `--resume`.
- `env.json` says `host.bare: true`; `SESSION.md` line 2 says `bare`.

## Replay (`snapper replay`) and check (`snapper check`)

A hidden Electron window (shown with `replay --headed`), `backgroundThrottling: false`, the same switches, its own throwaway profile (`%TEMP%\snapper-replay-<pid>` or `%TEMP%\snapper-check-<pid>`; the launcher's in-process replay and check use the launcher's profile), the session's window size (1280×720 if unknown). The game is served from the game root (`env.json` `game.root` when that folder exists on this machine, else the root `snapper import --root` recorded in the session's `import.json`) by the same kind of static server with the session's `--coi` setting (a URL session is loaded at its URL; `check` serves the game root you name, i.e. the current code), booted with the session's pause parameter (default `paused`) and the segment's query. The SDK is injected the same way with a bridge that records nothing (its flush timer still runs and discards); there is **no preload and no overlay**. CDP `Page` and `Runtime` are enabled and focus emulation is requested; console errors and exceptions are kept for `replay.json`. The game is driven only through its own SDK surface: `pause()`, `step(n, codes)` with the recorded inputs, `frame()`, `state()`, and its frame provider (or `webContents.capturePage()` when it has none). Audio is not muted. Replay writes `marks/NNNN/replay/` and regenerates `SESSION.md` and `SESSION.html`; `check` steps from mark to mark, booting once per tape segment, writes `check.json` outside the sessions, and writes into a session only `marks/NNNN/expected.json`, only with `--accept`.

## Attach mode (`snapper attach`, v1.4)

The game runs in a browser **you** started (Chrome, Edge, or the game's own Electron or NW.js shell) with `--remote-debugging-port`; Snapper reaches it over that port's DevTools WebSocket. Snapper starts no game window and changes no flag, setting or profile in your browser: the remote-debugging port and the separate `--user-data-dir` are yours (Chrome 136+ and current Edge refuse remote debugging on the default profile). The Snapper process runs one hidden `about:blank` window of its own to compose the `before/` sheet, with a throwaway profile (`%TEMP%\snapper-attach-<pid>`).

**There is no preload.** Everything the play window's preload does (the frame-interval recorder, the key and gamepad recorder, the pacing auto-marks, the overlay) is one script, `packages/host/preload/page.js` (the same code the play preload embeds), injected into the page's **main world**, not an isolated one: game code could see and change what it adds. It adds the globals `snapper` (the SDK), `__snapperHostBinding` (a function, the page-to-host channel), `__snapperBridge` and `__snapperPage` (both non-enumerable), and the same overlay `<div data-snapper-overlay>` with a closed shadow root. It runs in the top frame only; the SDK, as in play, in every frame (with `--no-reload`, only in the open top document). The Snapper process itself runs with the same Chromium switches as play; they apply to its own hidden window, not to your browser.

**What Snapper sends to the page, in order:** `Page.enable`, `Runtime.enable`, `Log.enable`; one page-info `Runtime.evaluate`; `Browser.getVersion` (else an HTTP GET of the endpoint's `/json/version`); one `Runtime.evaluate` that measures 40 animation frames in the page (the display rate; it waits up to 3 s, and in a hidden tab `env.json` `display.hz` stays null); `Runtime.addBinding` (`__snapperHostBinding`, re-added after `Runtime.executionContextsCleared`); `Page.addScriptToEvaluateOnNewDocument` twice (the page script, then the SDK); `Page.startScreencast` (not with `--bare`; the same JPEG 50 %, 480 px parameters and 7.5–14 fps tuner as play); then **one `Page.reload`** so the game boots with the SDK present and registers its state and stepper (the tape starts at that boot). A reload is a reload: unsaved state in the page is lost and its load-time side effects run again. Before any of this, `snapper attach` reads the endpoint's HTTP `/json/list` to find the page. With `--no-reload` instead, both scripts are also evaluated into the open document and nothing reloads (they stay registered, so a later navigation in the tab gets them too); the game's providers registered before Snapper came are missing, and every mark is recorded `replayable: false`. During the session: `Runtime.evaluate` for the SDK reads (ready, frame, state, flush, the F9 panel's commands, pause/resume/step) and for the host-to-page overlay messages (`__snapperPage.msg`); `Page.captureScreenshot` (PNG, the page at its own size and device pixel ratio) at each mark, after the overlay-hide request has gone to the page and come back through the binding, abandoned with a warning after 15 s; `Page.screencastFrameAck`. Events used: `Runtime.consoleAPICalled`, `Runtime.exceptionThrown`, `Log.entryAdded`, `Runtime.bindingCalled`, `Runtime.executionContextsCleared`, `Page.frameNavigated` (top frame), `Page.loadEventFired`, `Page.screencastFrame`. Console lines and errors logged before Snapper attached are not captured. Never: `Network`, `Fetch`, `Storage`, `Target`, `Runtime.removeBinding`, or any browser setting.

**Not scoped to one site.** The two scripts stay registered for the whole session: if the tab navigates elsewhere (a login page, another site), the page script, the key recorder, console capture, ring frames and mark screenshots follow it. As in play, the key recorder logs **every** key code with its time, including text typed into any field of whatever page is in that tab; shots and ring frames show whatever the page shows; `session.jsonl` and `env.json` hold the full page URL with its query.

**Only with `--smoke`** (tests): `Emulation.setFocusEmulationEnabled` (on, then off at the end), and the script's own `Input.dispatchKeyEvent`, `Page.navigate` and `eval` steps.

**Hotkeys** are the page's own `keydown` events, so they work only while the game page has focus: the mark, overlay, save, pause and step keys (with or without Shift) are stopped in the capture phase, including their auto-repeats, and their browser default is prevented; their keyup is stopped when the keydown was; Ctrl/Alt/Meta combinations pass through. They are taken even while the note box has focus (F8 there raises another mark). F5, F11 and F12 stay the browser's.

**On the way out.** On Ctrl+C or at a smoke's end the socket is still open: the `exit` state is read (one evaluate), `Page.stopScreencast` is sent (not with `--bare`), the page script gets `dispose` (the overlay, listeners, timers and its animation-frame loop are removed and its channels go quiet), the two scripts are removed with `Page.removeScriptToEvaluateOnNewDocument`, and the socket closes. When the tab or the browser closes, the socket is already gone: none of that is sent, and the session ends without an `exit` state. Snapper never closes your tab or your browser. Until the open document reloads it keeps `window.snapper` (its 250 ms flush timer keeps running with nothing to send to), the inert `__snapperBridge`, and the `__snapperHostBinding` function (the binding is not removed).

**Where the files go:** with `--game-root`, that game's `.snapper\sessions\<slug>\`; without it, `%APPDATA%\Snapper\attach-sessions\<slug>\` (or `--out`). Marks are recorded `replayable: false` with `--no-reload`, and also without `--game-root` when the page is not an http(s) URL (replay would have nothing to load).

**Recorded:** `env.json` `host.adapter: "cdp"`, `host.attach` (endpoint, target URL and title, the browser's product string, user agent, `reloaded`), `display` and `window` from the page, `gpu: null`.

**Measured (Z3, 2026-10-22, the demo, 4 marks per run, `perf.json` `host`; `scripts/verify-attach.mjs` reproduces it):**

| run | overlay-hide round trip, median (mean) | mark capture, median (mean, range) |
|---|---|---|
| play (preload IPC) | 9.4 ms (9.2) | 94.9 ms (96.2, 87.7–107.4) |
| attach, a second Electron | 8.9 ms (9.3) | 69.7 ms (70.9, 65.2–80.0) |
| attach, Edge 155 headless | 9.0 ms (9.1) | 62.1 ms (66.3, 58.8–83.4) |

The binding round trip is not measurably different from the preload's IPC (n = 4 per run; both include the page's two animation-frame waits, which a bare session skips only at its first mark, before its overlay exists). The Edge row is headless and the attach target a second Electron: a visible Chrome or Edge tab was not measured. An attach capture took 25–33 ms less wall time than a play capture in these runs (medians); why was not established (the attached page is not Snapper's own window, and its screenshot is taken by another browser process). The frames a mark costs an attached game were not measured separately; the play-mode measurement below is the reference.

## Tester mode (`play --tester`, the playtester kit, v1.4)

Everything in "Play" above, plus: the overlay asks the tester's name (on every run until a name is stored: Esc, a blank name or "anonymous" store nothing; keys typed there never reach the game, like the note box) and the host writes it to `tester.json` in the kit folder (the parent of the game folder; never in Snapper's own user data) and to `env.json` `tester`; the chip shows "F8 marks a moment" (the configured mark key) for the first 10 s after the game is ready (a toast in a bare session); the note box asks "What happened?". When the window closes the finished session folder is zipped to `<kit>/outbox/<slug>-<session id>.zip`, the game window shows "Send this file to <developer>: outbox\…" for about 2 s, and Windows Explorer opens on the zip (if zipping fails, the toast names the session folder to send instead). The zip is the whole session: every recorded key code, every screenshot and ring frame, the console, `env.json` (OS, GPU, display, local paths such as the game folder and Snapper's exe) and the tester's name; README-TESTER.txt tells the tester that it records a screenshot, the game's state, the last seconds of frames and their keys, and that nothing is uploaded; it does not list the machine details. **No network**: nothing is uploaded or sent; the tester sends the zip themselves. The kit's `snapper.config.json` is the developer's effective config without `out` and `discordWebhook`, plus `slug`, `developer`, `tester: true` and `pack` (the commit it was packed from); `snapper pack` leaves out the game's own `snapper.config.json` (it could hold a Discord webhook), any folder named `.git`, `node_modules`, `.snapper`, `.claude` or `dist` at any depth (a game that needs one of them at run time is packed broken), a root `outbox/`, anything `.snapperignore` lists, and the zip itself.

## The measured overhead (Y5)

Ring buffer on vs `--bare`, 2026-10-21, on the build machine (3440×1440 at 180 Hz, RTX 5070 Ti, the play window at 1080p), with no known load on the machine. Measured with `scripts/verify-trust.mjs`.

**Frame pacing.** Three runs per condition, alternating. Each run is a scripted ~23 s of input (D or A held, Space taps) with marks at ~12 s and ~23 s; each mark's `perf.json` covers the 10 s before its trigger, so a run's two windows hold about 3,600 rAF intervals and do not contain the captures themselves.

| game | condition | avg frame interval | p95 | max | drops (> 11.1 ms) | mark capture (wall) |
|---|---|---|---|---|---|---|
| demo (plain canvas) | ring | 5.56 ms | 5.6 ms | 5.83 ms | 0 | 87.3 ms |
| demo | `--bare` | 5.56 ms | 5.6 ms | 5.77 ms | 0 | 85.3 ms |
| Moonflex 1-1 | ring | 5.57 ms | 5.6 ms | 49.9 ms | 1 | 79.1 ms |
| Moonflex 1-1 | `--bare` | 5.57 ms | 5.6 ms | 48.1 ms | 1 | 78.3 ms |

- **The ring buffer, the chip and the status poll do not change frame pacing measurably**: average (5.56 ms is the 180 Hz period), 95th percentile and drops are identical, and the max is within the run-to-run spread (demo 5.7–6.0 ms in all six runs; Moonflex 49.9–50.0 ms ring, 44.4–50.0 ms bare).
- Moonflex's one drop, a 44–50 ms frame, appears in every run of both conditions: not the ring or the chip; its cause was not established (the game, the input, or Snapper's always-on parts).
- What the always-on parts (SDK, preload recorders, CDP) cost was not measured: there is no run outside Snapper here. To rule them out, compare with the game outside Snapper.
- A first run of the same A/B about 20 minutes earlier averaged 6.7–6.8 ms in both conditions (an unidentified load on the machine). It showed the same frame pacing in both conditions; its Moonflex mark capture was 8.8 ms slower with the ring; the quiet re-run gave +0.9 ms, and the 2026-10-22 runs below gave +6 to +11 ms again.

**The mark itself.** The capture took 64–93 ms of wall time per mark on 2026-10-21 (means 78–87 ms) and per-run means of 81–109 ms on 2026-10-22, 1–11 ms more with the ring, varying by run and machine state (2026-10-21: about 2 ms more on the demo and 1 ms on Moonflex; 2026-10-22: +2 to +5 ms on the demo and +6 to +11 ms on Moonflex, on the 1.3 and the 1.4 code alike), against a spread of 20–30 ms between marks or runs of the same condition. To see what it costs the game, two marks 4 s apart put the first mark's whole capture inside the second mark's window; every frame over 11.1 ms in the 1.2 s after the first mark was recorded with its end time (2 runs per condition per game, `capture-stall.json`):

| game | condition | frames over 11.1 ms in the 1.2 s after a mark (ms, ending at ms after the trigger) | worst frame elsewhere in the window |
|---|---|---|---|
| demo | ring | 22.2 @ 182, 33.3 @ 454 · 27.7 @ 181, 27.8 @ 448 | 16.6–22.2 ms |
| demo | `--bare` | 16.7 @ 91 · 16.6 @ 102 | 22.3–27.8 ms |
| Moonflex 1-1 | ring | 22.2 @ 86, 27.7 @ 186 · 22.2 @ 85, 11.2 @ 185, 11.2 @ 369 | 77.7–77.8 ms (its start-up frame) |
| Moonflex 1-1 | `--bare` | 22.2 @ 84 · 22.3 @ 76 | 77.8 ms (same) |

- **A bare mark costs the game one long frame of 17–22 ms** (3–4 display frames at 180 Hz), ending at the end of the capture's wall time, within 3 ms (76–102 ms after the trigger; the captures took 79–99 ms in these runs). Moonflex's ring-on marks show the same frame.
- **With the ring on, one or two long frames of 11–33 ms come about 180–455 ms after the trigger**, after the capture has finished: the time when the host re-encodes the ring frames and composes the `before/` sheet (a timing correlation; the cause was not isolated). The demo's ring-on marks show only these. Bare marks show none.
- These are below the pacing auto-mark's 250 ms single-frame threshold and are not the 10-frame run it also triggers on; still, the half second after a mark is not representative, and a game's own `console.error` or exception triggers such a mark by itself.
- These are two games on one machine. For a timing bug, compare with `--bare` and with the game outside Snapper.

**Re-measured for 1.4 (2026-10-22),** after the preload's page-side code moved into `page.js` and the capture pipeline into `capture.mjs`: the same A/B gives identical frame pacing again (avg 5.56 ms demo, 5.57 ms Moonflex, p95 5.6, drops 0 and 1 in both conditions; Moonflex's one long frame 55.5–55.6 ms in every run, 50–61 ms across the same-hour runs). Mark captures took longer than in the 1.3 runs (means 98–100 ms demo, 88–98 ms Moonflex), so the 1.3 code was run back to back with the 1.4 code on the same machine the same hour: 1.3 averaged 101.4 / 96.0 ms (demo ring / bare) and 97.2 / 88.8 ms (Moonflex), 1.4 100.8 / 97.9 and 94.4 / 88.0. The refactor did not change the numbers; the machine was slower that day than on 2026-10-21 (cause not identified).

## How to answer "was it Snapper?"

1. Read the mark's `perf.json` `host`: whether the session ran bare, how many ring frames were held, and how long every mark's capture took so far (`markCaptureMs`). A long frame in the half second after an earlier mark is most likely that mark's processing (with the ring on, up to about 0.45 s after it; the mark times in `session.jsonl` give the offsets); check whether `--bare` shows it.
2. Play the same spot with `--bare`. If the bug stays, the ring buffer, the chip and the 500 ms poll were not it.
3. Replay the mark: the replay has no preload, no overlay, no screencast and no real time. If the replayed state shows the bug (`stateMatches: true`), the game's state at that frame follows from its inputs. That does not clear frame timing, rendering or audio, which the replay does not reproduce (and with no state provider, `stateMatches` proves nothing; the replay says so).
4. Open the game's `index.html` through any static server without Snapper. A game that guards its calls as `SDK.md` requires is meant to behave identically there; that is the game's contract, not something Snapper checks.
5. Run the no-Snapper repro (v1.4): `snapper export-repro <session> <mark> --inject`, `snapper serve <…>/repro/repro-game`, open the URL the repro's `README.md` names (the served page plus the session's query, the pause parameter and `snapper-repro=1`, e.g. `/index.html?paused&snapper-repro=1`) in Chrome, Edge or Firefox.
